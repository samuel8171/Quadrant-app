用户报告三条：

> 图三：我的的趋势图荧光条在液态玻璃下没有模糊，其他情况下底部栏的模糊正常

## 缺陷三：趋势图荧光条没被 dock 的材质糊

### 现象与初次量化

`scripts/trend-chart-glass.mjs`（视口 375×667 —— **只有短屏**趋势卡才天然压在 dock
后面，390×844 下 overlap 恒为 0，量不出东西）。

第一版判据只有保留率，读数是：

| 档位 | 保留率 | 初判 |
| --- | --- | --- |
| fallback（iOS，报告者所在档） | 0.218 | ❌ 死/未糊（贴着 0.2 门槛） |
| chromium | 0.143 | 活 |

保留率把 fallback 判成"压线未过"，但**这个结论是错的**，而且 chromium 的 0.143
更是明确说"活的"。若只看这一列，会得出"其实没问题、只是临界"的错误结论。

### 为什么保留率判不出来

缺陷的真相不在"糊了多少"，而在**绘制顺序**：材质板画在 `.sidebar` 的 50% 保底底
**之下**，所以板上糊出来的那份被盖住，眼睛看到的是那层底之下透上来的**未糊**内容。
此时像素仍有变化（底在变色），`std` 比值会掉到一个"看着接近活"的数 —— 它是
两个效应相抵的假读数，不是材质真的在输出。

### 单变量消融（`scripts/paint-order-ablation.mjs`）

同一帧、同一 x 列、只动绘制顺序，量荧光线的峰值与半高全宽（DPR 2）：

| 组 | 改动 | 峰值蓝 | FWHM |
| --- | --- | --- | --- |
| A base | 现状（板在下） | 94 | 4 |
| B | 板抬到 `.sidebar` 之上（300） | 17 | 130 |
| C | `.sidebar` 降 `z-index: auto` | 178 | 11 |
| D | `.sidebar` 底透明（板仍在下面） | 178 | 4 |

- **A**：FWHM 4 设备像素 = **2.0 CSS 像素**，恰好等于 `stroke-width: 2`
  ⇒ **一点都没糊**，是一条锐利亮线压在磨砂底栏上。
- **B/C**：糊了（FWHM 130 / 11）。
- **D 是关键**：把保底底拿掉，板依然没输出到这条线上 ⇒ 不是"被底盖住的错觉"，
  而是**板画的整块（含它糊出来的那份）都在 `.sidebar` 之下**。

### 修法

`components/glass/glass.css`：

```css
.gs-layer--dock .gs-plate {
  z-index: 103;
}
```

`.nav` 实测 `z-index: auto`，板是「定位 + 非 auto 的 z」⇒ 一定画在 `.nav` 之前
（即下层，符合"材质是背景、按钮在上面"的既有意图）；103 显式压过 `.sidebar`
自己的 100；103 < 110（手机菜单）⇒ 菜单仍压在 dock 之上。

**不能**靠调 `.sidebar` 的 z-index 或那层保底底来修：100 是手机档全局层级的一环
（菜单 110、遮罩 120 都要压它）；把保底底调淡更是反效果（底越淡，未糊内容越显眼）。

验后：`liquid-glass-probe.mjs` 39/39 通过（含"菜单层级压过 dock"那条）、
`dock-glass-retention.mjs` 两档仍 alive（0.028 / 0.049）、五个导航项
`elementFromPoint` 全部命中自身。

### 判据的演进（踩过两次，别退回）

`scripts/trend-chart-glass.mjs` 现在有**两条**判据，只留一条会漏：

1. **保留率 ≤ 0.2** —— 材质确实在输出。单靠它在本次差点放过缺陷。
2. **sharpRatio = 峰值(材质开)/峰值(材质关) ≤ 0.6** —— 输出的是"糊过的"那份。

第 2 条的实现绕过两个坑：

- 坑一（第一版）：用「蓝 − 红」沿固定列扫 FWHM。但条纹跳变本身就带一大片
  蓝−红信号且幅度（178）远高于线本身（94），"最强列"必然被条纹抢走 ⇒ 量到
  59px 的假 FWHM。**改用峰值而不是宽度**：线未糊 94、糊过 ~17，两道山峰分得很开；
- 坑二：绝对峰值随条纹相位与卡片位置漂移，所以要用**同一次运行里"材质关"那张**
  做分母。实测修好前 1.00（两张峰值逐字相同）、修好后 0.23 / 0.33。

探针已做过反向验证：临时注释掉 `z-index: 103` 后 sharpRatio 立刻回到 **1**，
报告判 ❌ —— 这条判据是真的在守。

## 缺陷一/二：日结栏压在状态栏羽化带上 + 与下方间隔

### 几何事实（`scripts/statusbar-clearance-probe.mjs`）

日结栏是**唯一一个自己写顶部安全区的页面元素**：宿主 `.weekly-shell` 是
`flex: 1` 的纵向 flex、本身没有内边距，所以 `.settle-card` 的 `margin-top`
就是卡片到屏顶的全部距离。

把 `--safe-top` 改写成真机值（iPhone 14 Pro = 59）后：

| 量 | 改前 | 改后 |
| --- | --- | --- |
| 卡片盒顶 y | 73 | 83 |
| 状态栏羽化带下沿（safe-top + 14） | 73 | 73 |
| **墨迹余量**（盒顶 − 羽化带下沿） | **0** | **24** |
| 卡片 → `.weekly-page` 的间距 | **0** | **24** |

- 余量 0：卡片上边框正好压在羽化带的最后一行像素上 ⇒ 用户说的"被状态栏模糊遮挡"。
- 间距 0：`.weekly-page` 的 `padding-top` 是"面板到它自己内容的距离"，**不是**
  "上一个兄弟到面板的距离"。卡片下方的 64px 空档全来自 `.weekly-page` 的
  padding（73 + 45 = 118，而标题要到 201 才出现）⇒ 用户说的"与下方间隔"。

### 修法

`styles/theme.css` 手机档：

```css
.settle-card {
  margin: calc(24px + var(--safe-top)) 20px 24px;
}
```

顶部的 24 与 `.page` 系列 `calc(24px + var(--safe-top))` 的口径统一；
底部的 24 是"卡片 → 面板"的呼吸，与 `.weekly-page` 的 `padding-top` **不是同一个
量**（后者是"面板 → 面板内标题"），二者都取 24 是因为它们在这条纵向节律里
扮演同一个角色，不是为了相互抵消。

### 判据（`scripts/statusbar-clearance-probe.mjs`）

已把这个探针扩了两处：

1. 种子里补上**逐字段合法**的 `money` 块（否则整份种子静默作废、卡片不渲染）；
2. 目标表里加 `.settle-card`，并支持两件新东西：
   - `padTop` —— 容器类元素的"盒顶到墨迹"的距离（取容器自己的上内边距）。
     用标题那套 `(lh − fontSize)/2 + fontSize×0.2` 会算出 ~3px，严重低估；
   - `marginBelowSafeTop` —— **盒顶距 safe-top 的差值**，三档机型应当给出同一个数。

⭐ 判据**不是**"离 safe-top 多远"（`CLEARANCE_TARGET = 12` 是给标题的口径）。
日结栏的问题从来不是"被裁掉"，而是**和页面其它内容的顶部留白看起来不一致**
（`.page` 系列统一 24，卡片当时只写了 14）。差值口径才抓得住它。

反向验证：改回 `calc(14px + var(--safe-top)) 20px 0` 后，三档机型齐刷刷
`14 / 24 ❌ 节律不符`，探针以退出码 1 结束。恢复后三档都是 `24 / 24 ✅`。
