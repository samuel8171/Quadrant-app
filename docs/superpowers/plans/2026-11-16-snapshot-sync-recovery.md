# 快照同步与存档恢复实施计划

目标是阻止旧快照覆盖，并让桌面、Web 与云端对历史存档有一致的读取语义。

## 约束

- 网页端保留自动同步。桌面端保留手动操作及预览确认。
- 只有确认无云端记录才执行首次写入。已存在的行始终校验基准修订。
- 历史字段补默认值时保留结算事实、原日期、启用日期的缺席和未知字段。
- 损坏或超前版本仅供恢复查看，原始存档保留。
- 分支本地验收。生产先增加写入入口，再发布网页、确认活动标签已刷新，最后收紧旧直写权限。

## 步骤

- [x] 先在 Web 存储与 Store 的现有入口添加回归用例，覆盖缺配置键、坏云端正文、排队回写、离线删空和本地写失败。
- [x] 在 shared 提供 AppData 解码，迁移已知旧格式，对恢复预览保留状态。接入 Web、IPC 和云端读取。
- [x] 由快照同步模块串行处理落盘、对账、冲突副本与手动确认。浏览器原子存储快照及对应待同步元信息。
- [x] 实现数据库条件写入及独立收口 SQL。测试同一修订并发、竞争建行、跨账号拒绝和旧客户端过渡。
- [x] 跑 TypeScript、Vitest、Web/Electron 生产构建和独立评审。


## 上线顺序

1. 在独立 Supabase 环境核对 user_data 与附件访问规则，再执行 supabase/migrations/202611160001_snapshot_revision.sql。它允许 1.4.2 在过渡期按旧方式工作，每次旧写入同样推进新修订号。
2. 将新网页部署到现有地址。在刷新仍开着的旧标签前核对最新本地改动。刷新后检查修订读写与已存在账本。新版安装包在同一数据库上验收手动确认、上传与恢复。
3. 确认新版客户端均已接管后，单独执行 supabase/cutover/disable_legacy_snapshot_writes.sql。验证旧直写权限已关闭，登录用户仍可读取自己的快照并通过条件写入函数提交。
4. 切换期间如需回滚，数据库还需提供与旧客户端配套的直写权限。回滚网页构建本身不会恢复数据库权限。

原始存档异常时应用展示只读预览。Web 冲突副本可从页面下载。旧版最后一次记录的时间戳与新版 UUID 采用不同的修订格式，首次对账若发现分歧，按云端优先保留本地待上传副本。
