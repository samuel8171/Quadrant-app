## 1. 一句话概括这次修订

把「时币」从「只有做事才花」改成**带四象限权重的做事成本**，把「娱币」从「只由表现浮动」改成
**另有两条纯消费来源（刷视频 / 打游戏）**，把「日结」从「只问有计划的日子」改成
**固定回溯 7 天、可标记休息日、逾期即按满额扣款**，并把数值定标到用户给的一套具体数字上。

## 3. 时币的完整计算式（取代旧 §6.2 / §6.3）

### 3.1 单条事件计费

```
dayMin   = actualMin − nightMin
base     = (dayMin + nightMin × nightMultiplier) / 60 × tcPerHour
costTC   = round(base × quadrantMultiplier[quadrant])
```

- **深夜倍率与象限倍率相乘**，且深夜倍率只作用于落在 `[23:30, 06:00)` 内的那部分分钟数（旧规则不变）。
- 象限即「重要 × 紧急」的二维：**Q1 重要且紧急 / Q2 重要不紧急 / Q3 不重要但紧急 / Q4 都不**。
  倍率已定：**Q1 1.5 / Q2 1.0 / Q3 1.2 / Q4 0.5**。用户的权重取向是 **紧急 > 重要**
  （故 Q3 = 1.2 高于 Q2 = 1.0），两者皆有取最高（Q1），两者皆无最低（Q4）。
- `costOfEntry` 签名相应扩展，须能拿到象限（见 §8 的接口变更）。

### 3.2 日结算

```
dayLimit_i  = max(dailyCapTC × minCapRatio, dailyCapTC − overdraft_{i−1})
spentTC_i   = Σ costTC（当日全部条目）
overdraft_i = max(0, spentTC_i − dayLimit_i)      # 只带入次日，不累积
deltaLT_i   = Σ leisureDelta（条目奖惩）
              − 刷视频小时 × videoLTPerHour
              − 打游戏小时 × gameLTPerHour
```

**日超限与周超限是两条独立的线**（用户裁定第一条，与已实现行为一致）：

| 触发 | 后果 |
| --- | --- |
| 当日花费 > 日软上限 | 超出部分**只侵蚀次日额度**（`overdraft` 只带一天，有 20% 保底） |
| 当周花费 > 周总额 | 才惩罚**下一周**的周总额与周娱币 |

日超限**不**直接罚周、也不减少娱币额度。这条已在 Task 4 的裁定中确立，R2 不变。

## 4. 日结范围与逾期（新增）

| 规则 | 内容 |
| --- | --- |
| **问询范围** | 固定回溯 **7 天**：`today − 7` 到 `today − 1`，**不再限于「有计划事件的日子」**。没有安排计划的天同样要问 |
| **已结算不可重结** | 一天一旦结算过，就**不允许再次触发日结**。这条针对「往日时间轴被修改」的情况 |
| **逾期即放弃** | 超出 7 天窗口的未结算日视为**放弃日结**：按**时币当日全扣**，**娱币不扣** |
| **休息日** | 某天可标记为休息日；休息日「仅扣除当天 80% 的时币」—— 基数待确认 |

⚠️ 这三条**推翻**了 Task 8 已实现的两处行为，必须修正：

1. 现在的 `ensureLedgerDays` 只补建**有计划事件**的过去日；R2 要求补建**窗口内全部过去日**。
2. 现在的 `pendingDays` 依赖既有记录；R2 的窗口是固定的 7 天，逾期不是「不出现」而是「按满额扣款落账」。

## 5. 娱币的完整来源（取代旧 §6.4）

娱币有**三类**来源，其中前两类是「事」，第三类是「消费」：

| 类别 | 触发 | ΔLT |
| --- | --- | --- |
| **表现浮动**（旧规则保留） | 没做 `!done` | `−missPenaltyLT` |
| | 低效 `actualMin > plannedMin × 1.5` | `−penaltyLT` |
| | 高效 `actualMin ≤ plannedMin` | `+rewardLT` |
| | 计划外且已完成 | 0（不入任何类） |
| **纯消费**（新增） | 刷视频 `h` 小时 | `−h × 1` |
| | 打游戏 `h` 小时 | `−h × 1.5` |
| **深夜刷手机**（新增） | 见 §6 | 扣大量娱币 **且** 扣大量次日时币 |

⭐ **刷视频与打游戏不呈现在周计划里**，只在**日结时**被问到：

- 「今天刷视频用了多久时长？」
- 「今天打游戏用了多久时长？」

这两问**只扣娱币**，不产生任何时币消耗，也不进 `quality` 四分类（它们不是「计划内/计划外事项」，
而是与计划无关的消费记录）。

## 6. 深夜刷手机的次日连带扣款（新增）

日结时问：**「昨天 24:00 后还有没有刷手机？」**

- 答「有」⇒ 扣除**大量次日金钱（时币）与娱币**。具体数额待定（见 §9），但机制是
  **跨日结转**：扣款落在**次日**，而不是问话当天。
- 与已有的「昨夜 23:30 之后还在做事吗」（`nightPending` / `openNightsBefore`）是**两个不同的追问**：
  前者问的是**做事**（按时长×倍率计入时币），后者问的是**刷手机**（定额扣次日时币 + 娱币）。
  两者都要保留，实现上应在同一次日结里并列问出。

## 9. 语义裁定记录

### 9.1 已决（2026-09-30）

**逾期未结算日「时币当日全扣」= 扣 `dailyCapTC` 全额（80），娱币不动。**
即：拖过 7 天不问，那天就按 80 币记一笔 —— 不看你做了什么，也不看你计划了什么。

**象限倍率 = Q1 1.5 / Q2 1.0 / Q3 1.2 / Q4 0.5**，权重取向「紧急 > 重要」。
两条推论是有意为之，不是副作用，实现时不要「顺手修正」：

- **Q3（不重要但紧急）比 Q2（重要不紧急）更贵** —— 系统对「被紧急事推着走」收费更高，
  这正是艾森豪威尔矩阵想纠正的那件事。
- **Q4 = 0.5 让不重要不紧急的事最便宜** —— 因为「无意义消耗」的惩罚通道在娱币
  （刷视频 / 打游戏）那边，不必在时币上重复收一遍。

### 9.2 仍待确认（阻塞 R2-E）

**休息日「仅扣除当天 80% 的时币」的基数是什么？**

- (a) 日软上限的 80%（= **64 币**），即休息日固定扣 64；
- (b) 该日实际活动应扣金额的 80%（**打 8 折**）；
- (c) 其他。

这决定休息日比平时**便宜还是贵**，直接影响体验。R2-A ~ R2-D、R2-F ~ R2-J 均**不依赖**它，
可先做；**只有 R2-E 被它阻塞。**

## 10. liquid-glass 对新增内容的跟进方案

**结论：默认不玻璃化新增的常驻内容；只对新增浮层做，且必须逐个过验收口径。**

### 10.1 为什么不给「我的」页的小组件加玻璃

玻璃材质要有意义，**身后必须有内容可糊**。小组件卡片是「我的」页的**常驻布局元素**，
背后是页面背景色，采不到任何有结构的背景 ⇒ 加了 `backdrop-filter` 也只能糊自己身后那一片纯色，
观感与不加几乎相同，却要付全部开销。这不是猜测 —— 本项目已在桌面端侧栏遇到过同一情形：
`glass.css` 里 `.gs-layer--dock` 在桌面端就是 `display:none`，理由写在注释里：
「桌面端的 `.sidebar` 是 flex 兄弟、身后没有内容，模糊与折射都无对象可作用」。

### 10.2 哪些新增浮层值得做，以及代价

| 浮层 | 值得做？ | 理由 |
| --- | --- | --- |
| **日结面板** | ⚠️ **倾向不做** | 它是**每天开一次**的高频浮层，而 `shader` 档每开一层要卡主线程约 1.3 秒（StrictMode 下翻倍）。这在本项目是已实测的数，日频交互付不起 |
| **象限计费气泡** | ✅ 可以 | 小面积、低频，且身后是四象限画布，有可糊的内容 |
| 待结算卡片 | ❌ | 它是页面内联内容，不是浮层 |

### 10.3 若要做，必须走的验收口径（不可省）

每一层新的玻璃宿主都要**逐条**满足下面这些已固化在项目里的约束，缺一条材质就会「只剩染色」：

1. **材质板是面板的兄弟**，挂在锚点层；不能进库子树，锚点也不能带 `transform`。
2. 从材质板往上到 `body` 的整条祖先链上**不能有合成面**：`fixed` / `sticky` / **非 auto 的 `z-index`**
   任一出现，材质就只剩染色。层级统一走 `--gs-z`。
3. 位移滤镜**只能写在 `backdrop-filter` 的 `url()` 里**；挂成材质板自己的 `filter:` 会让材质整个消失。
4. `url(#滤镜)` **绝不能进玻璃层的 `backdrop-filter`** —— 它会替换前一步 `blur()` 的输出，表现为整块变透明。
5. 浮层盒子**不能用 `inset: 0` 定高**，要 `height: max(100%, var(--app-height, 0px))`。
6. 手机端走 `fallback` 档，改结构后必须把 `forceEngine` 设成 `fallback` 再验。

### 10.4 验证方法只有一个口径

**保留率**：条纹插在被测浮层**之前的页面侧** → 同状态抓「材质开 / 材质关」两张 → `std(开) / std(关)`。

- **≈0.66 正好 = 1 − 染色 0.34 ⇒ 只剩染色，材质是死的**；
- **≤0.2 才算活**。

像素差判不出来（染色本身就产生大量像素差）；把条纹插在同一层里也判不出来。

### 10.5 我的建议

**R2 不新增任何玻璃宿主。** 先把功能做对、把数值定标跑一周拿到真实手感；玻璃是纯装饰，
且每加一个宿主都要重走上面 6 条约束 + 保留率验证。等 R2 功能稳定后，若要加，
按「象限计费气泡 → 日结面板（先量 shader 档的实际卡顿）」的顺序推进，一次只加一个宿主并单独验证。
